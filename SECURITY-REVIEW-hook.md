# Security review: argv-level rules in the Muse Code hook

## Scope

This review covers how `swarm/hookio.py` reads shell calls and how `swarm/state.py` loads manifests that hold argv-level atoms. The hook classifies text. It never runs it. Authority (manifest, state, keys, journal) lives outside the governed repo, and the hook's argv pins where it is (`mandate-hook --state-dir <abs> --root <abs>`).

The protected directories `.mandate/` and `.muse/` are guarded against writes and execution, not against reading. The read tools (`read_file`, `grep`, `glob`, `search`) may read them inside the worktree. That is acceptable only because no shipped layout keeps a secret there:
- the hook refuses a state directory under the repo root;
- the console's `gate.key` lives in its own state directory;
- the governed repo template may not ship `.mandate/`.

A shell call yields one atom per command segment. Segments are split at `;`, `&&`, `||` and `|`. Most segments yield `cmd:<name>` for their first word. A binary that the manifest names with arguments (for example `cmd:nimbus deploy api-v2 prod-eu`) is argv-governed. Its command must stand alone in plain words, its atom is the whole argv, and any other shape matches no atom.

## Threat

An agent holds the release role and wants prod-eu to run anything other than `nimbus deploy api-v2 prod-eu` or `nimbus status prod-eu`. Its main target is the superseded `nimbus migrate migration-0017 prod-eu`. The agent writes the full text of every shell call and can build up shell state across calls.

## Method

- A corpus of bypasses, each pinned to its refusal reason (`swarm/test_hook_args.py`).
- The same corpus and more, run through the real hook under the Nimbus manifest (`swarm/test_hook_nimbus.py`).
- A differential run against real shells (`swarm/test_hook_shell.py`).
  - Recorder executables are the only programs on PATH, and each one logs the argv it was started with. `HOME` and `ZDOTDIR` point to an empty directory, and `BASH_ENV` and `ENV` are unset.
  - The test runs four shell binaries:
    - `bash` as found on PATH (Homebrew bash 5.3 on the development Mac);
    - `/bin/bash` (bash 3.2 on macOS; skipped when it is the same file as `bash`);
    - `zsh` (`/bin/zsh`, 5.9);
    - `sh` (`/bin/sh`, which is bash 3.2 in POSIX mode on macOS and dash on Debian and Ubuntu).
  - Every command the reader allows runs in each shell twice: once with recorders that succeed and once with recorders that fail, so both sides of `&&` and `||` run. For each allowed command:
    - the programs that ran must be exactly the reader's atoms;
    - every argv a recorder received must be one the reader parsed;
    - every argument (and each part of it split at `=` and `:`) must resolve inside the worktree and outside `.mandate/` and `.muse/`;
    - a governed command must run its argv exactly once.
  - The sandbox mirrors the live layout: an authority directory beside the worktree, and `.mandate/` and `.muse/` inside it.
  - Commands the reader refuses never reach a shell in this test. Their reasons are covered by the corpus tests only.
  - This covers:
  - a hand corpus run with `-c`;
  - persistent interactive sessions (`bash --noprofile --norc -i`, `zsh -f -i`, `sh -i`), with every line fed on stdin;
  - 400 generated commands and 150 generated sessions per shell;
  - recorders named after odd blank characters, so a segment made only of such a character shows up as a program that ran.
- An adversarial review of the reader against bash 3.2, bash 5.3, zsh 5.9 and sh, with about 60 hand-picked strings and about 13,000 fuzzed ones. No string made the reader yield `cmd:nimbus deploy api-v2 prod-eu` while a shell ran a different nimbus argv, another program or an extra program. The divergences it did find are findings F8 and F9 below. Later differential and review rounds found F12, F14 and F16.

The reasons below are the messages the hook returns. Run all the listed tests with:

```
.venv/bin/pytest swarm/test_hook_args.py swarm/test_hook_nimbus.py swarm/test_hook_shell.py "swarm/test_hookio.py::test_targets_wrapper_forms_map_to_their_first_token" "swarm/test_hookio.py::test_targets_reject_protected_shell_workdir" "swarm/test_hookio.py::test_targets_lead_cannot_work_in_a_child_worktree" "swarm/test_hookio.py::test_targets_reject_shell_workdir_escape" "swarm/test_state.py::test_manifest_refuses_ambiguous_argv_atoms" -q
```

The differential tests skip any shell that is not installed.

## Residual risks (documented, not closed)

- **R1. Startup files, shell options and PATH.** The hook reads only the text of the call. What a shell does with that text also depends on state the hook cannot see:
  - Startup files: zsh reads `$ZDOTDIR/.zshenv` (or `~/.zshenv`) even for `zsh -c` and expands the aliases defined there. bash reads `$BASH_ENV`, and an interactive sh reads `$ENV`.
  - Options set in those files: `set -k` / `setopt KEYWORD`, `MAGIC_EQUAL_SUBST`, `histchars`, `expand_aliases`.
  - PATH order: a macOS login shell runs `path_helper`, which can put `/usr/local/bin` or `/opt/homebrew/bin` ahead of the fixture's `bin`.

  An alias `cat='nimbus migrate migration-0017 prod-eu'` in `.zshenv` makes an allowed `cat RUNBOOK.md` (atom `cmd:cat`) run a migration. Within a session, the hook refuses `~` and absolute paths. No Nimbus role holds a file atom, and the builtins that change shell state are refused (F10). The agent's shell must still start from clean startup files and a PATH whose `nimbus` is the intended one. That is the operator's responsibility. The differential runs with empty startup files and recorder-only PATH, so it does not exercise this risk.
- **R2. Shells and interpreters are still ordinary command names.** `sh`, `bash`, `zsh`, `python` and other interpreters, as well as `make`, `git` (aliases) and test runners, map to `cmd:<name>`. Any of them can run `nimbus migrate` itself (`sh -c '…'` yields `cmd:sh`). Only manifest discipline keeps them out. The Nimbus manifest grants none of them. For other repos, Muse Code's OS sandbox and worktree isolation contain code that an allowed binary executes, not Mandate.
- **R3. The agent's actual shell is unverified until the live run.** The hook assumes that the `bash` tool runs `command` in a POSIX shell. bash, zsh and sh are checked, both with `-c` and as interactive shells fed through a pipe. Interactive shells attached to a terminal (where zsh runs its line editor) and other shells are not checked. The live test (`pytest -m live e2e/test_flujo_f_live.py`) fails unless the fixture CLI traced at least one invocation and every traced invocation came from bash, zsh or sh (dash counts as sh).
- **R4. The arguments of ungoverned commands are not inspected beyond path checks.**
  - For a command that is not argv-governed, the hook checks the name and refuses characters the shell would expand or read differently: redirection, substitution, `!`, globs, `=` words, tab and odd blanks.
  - It also refuses typed path tokens that escape the worktree or name `.mandate` or `.muse`. Because expansion is refused, the typed token is the argument the program receives (the differential checks this).
  - Anything else that `shlex` accepts passes: `cat 'a b'` yields `cmd:cat`.
  - Two cases stay outside these checks:
    - paths that an executed program builds itself (for example from its own configuration);
    - reads of `.mandate/` and `.muse/` through the read tools (see Scope).
  - This is safe only while no granted binary interprets its arguments as commands (R2).
- **R5. PATH belongs to the agent.** A role with file atoms on a PATH directory, or a relative PATH entry, could plant a `nimbus`. Nimbus roles hold no file atoms. The live run puts `<base>/bin` ahead of the inherited PATH, next to the repo and outside it. That entry is absolute when `MANDATE_FLUJO_F_DIR` is absolute or unset. Relative entries in the inherited PATH are not checked.
- **R6. MCP.** The hook refuses every MCP tool except the Mandate desk's, including harmless ones. The hook has no per-server MCP manifest.
- **R7. The live prod-eu is a fixture.** In the live run, prod-eu is `demo/nimbus_cli.py`, which records the release in the worktree and verifies no certificate. The release passes because the hook verifies the release agent's delegation chain on every call. The certificate-verified release is the pinned scenario.
