# Mandate

> Don't trust agents. Verify them.

Mandate is the independent authorization and verification layer between AI
agents and the world: no action touches money, data, or production without
a valid cryptographic certificate. No certificate, no execution.

With the holder copy of the receipt (it carries the action salt; see below), recompute the certified hash with `printf '%s' '<canonical action JSON>' | openssl dgst -sha256 -mac HMAC -macopt hexkey:<action salt hex>`; the digest must equal the certificate's `action_hash`. The canonical action is the `cava` object of the gate-signed SD-JWT payload with its `_sd` key removed and the disclosed `targets` restored (the `action_salt` Disclosure is the key, never part of the bytes), serialized with sorted keys, no whitespace (`,` and `:` separators) and ASCII only (non-ASCII as `\uXXXX` escapes): Python's `json.dumps(cava, sort_keys=True, separators=(",", ":"), ensure_ascii=True)`.

Verify a receipt: open `http://127.0.0.1:8766/console/explorer.html`, paste the payment id from the ledger (on the sandbox rail, the bank's transfer id), a receipt hash or action hash, or the receipt JSON from `/api/receipt/<id>` (the auditor copy: verified, personal fields withheld), and press `Load the holder copy` to see every field. Tick the fields an auditor may see (`Amount`, `Payee account`, `Debit account`, `Reference`, and `Holder identity` only to prove who approved) and press `Make the auditor copy` to get a receipt that discloses only those. A hash only locates the receipt: the explorer checks that the answer carries it, then verifies every step in the browser. The `Receipt hash` row shows the hash to quote; it is the same in every copy of a receipt. The `Gate key` field holds the key the server publishes at `/api/keys`, which only proves the receipt matches this server. To verify without trusting the server that serves the page, record the gate key through a channel you already trust (for example read `/api/keys` on the desk's own machine when the run starts) and paste that key into `Gate key` (`Pinned by you`); once loaded, the explorer verifies offline. `mandate-desk`, and `mandate-console` without `--state-dir`, draw a new gate key every time they start and do not persist it, so a receipt verifies only against the key of the run that issued it: after a restart, a saved receipt fails at `Gate certificate` (`Not signed by the gate key`) against the newly published key, and still verifies against the key you recorded for its run. With `--state-dir` the key is kept in the state directory and every receipt keeps verifying after a restart. The holder copy is served only to a loopback client (`127.0.0.1` or `::1`) that asked for a loopback Host (`127.0.0.1`, `localhost` or `[::1]`) and sent no proxy header (`Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP`, `CF-Connecting-IP`); anything else gets 403. This is not authentication: anyone who can open a loopback connection to the desk gets every holder copy. A production desk hands the holder copy only to the holder. `ARCHITECTURE.md` lists what a receipt reveals and what it cannot hide.

Live tests are opt-in and need `MODEL_API_KEY` or `META_API_KEY`, plus `BASETEN_API_KEY` for the attacker row and a logged-in `muse` CLI for the swarm row.

The real bank rail moves money between two Increase sandbox accounts, `checking-881` and `acme-991`, as an account transfer. Run `mandate-bank-setup` once to open both accounts and fund the payer, then start `mandate-console --rail sandbox --state-dir ~/.mandate-demo`; both read the key from `INCREASE_SANDBOX_API_KEY` and remove it from their own environment before doing anything else. The sandbox moves pretend money in Increase's ledger, a system we do not control. The transfer id (`sandbox_account_transfer_…` in the sandbox) appears in the desk result, the console, the receipt and the sealed registry entry. In Increase it is visible in the sandbox dashboard of the account that holds the key, which is private, so the demo shows it on screen. Template attacks (the forged approval included) always run on the simulated ledger, and every payment says which rail moved it. On the sandbox rail every payment starts from a holder-signed intent (the holder page); a quote without one, such as the WebMCP glasses flow alone, is denied `intent: missing` before the bank is called. The live tests pay between accounts of their own, `live-payer` and `live-payee`, so their transfers never appear in the demo account's reconciliation.

The sandbox rail needs `--state-dir`, so receipts outlive the process; without it `mandate-console` exits with `bank rail needs --state-dir: receipts must outlive the process`. The state directory holds the registry and its seals, the receipts, the spent certificates and consents, the holder intents, the paired holders, the simulated ledger and the gate key. `mandate-console` creates it with mode 0700 and takes its `lock` file, so a second console on the same directory exits with `state: directory in use`; a directory, `state.db` or `gate.key` that is a link, belongs to another user, or is open to group or others is refused at start. `gate.key` is the gate's private signing key (mode 0600). `state.db` is not safe to hand to an auditor either: it holds every holder copy (every Disclosure, the action salts, payee and debit accounts, references and the holder identity) and the certificates of payments still being settled. An auditor gets auditor copies from the explorer, never the file. Keep the directory outside any repository (`.gitignore` lists `gate.key` and `state.db*` as a backstop). A restart keeps every receipt verifying against the same published key, keeps every spent certificate, consent and intent spent, and numbers quotes and payments on. A normal stop closes the database, so `state.db` alone holds every commit. Without `--state-dir` the simulated rail keeps everything in memory, as before.

Command's `Transfers at the bank without a certificate` is read from the bank's own API by a read-only reconciler: it lists every account transfer that left the desk's debit account since the registry began and checks that each one carries the idempotency key of a certificate this desk issued and has a sealed execution entry in the registry; sealed payments the bank does not list are named in the evidence. It runs at start, every 60 s on the sandbox rail, and on `POST /api/reconcile` (body `{}`), and only reads: it never asks the bank to move money. The metric reads `<without a certificate> of <transfers> · SANDBOX increase · checked <time>`, the time of the last check; a check that could not run reads `not checked: <reason> · <time>`, and an intent the bank paid twice adds `· <n> paid twice` and turns the tile red. A payment whose bank call timed out (`bank: outcome unknown`), or whose process died during the call, is settled automatically: as paid, with a sealed entry and a receipt, once the bank lists its transfer complete, or as not paid once its certificate expired and 60 s more passed with no transfer under it.

On the sandbox rail the console also shows what the bank itself reports. Every 5 s it reads Increase's event list (`GET /events`, oldest first) for account transfers, ACH transfers, inbound ACH transfers, card payments and card authorization requests, and adds one `bank` line per new event, labelled `SANDBOX`, naming the event id and the object it belongs to; for a payment that is the same `sandbox_account_transfer_…` id the desk line shows. The read position and the ids already shown are kept in the state directory, so a restart never shows an event twice; a crash between saving a page and showing it can drop that page's lines from the console, which costs a display line and never money or a decision. Bank lines are observations: they never move money, never change a decision and are not counted as decisions; Command counts them under `Bank events`, with how many verified sandbox payments a bank event names. The events are those of every account the key can see, the live tests' accounts included, and an event names its object only: its amount and status are in the Increase dashboard. The simulated rail has no bank of its own to report, so it shows no bank lines.

With `--two-step`, each quote appears in the Increase dashboard as a transfer awaiting approval, holding the amount, until the holder approves on the device and the certified confirm approves it at the bank. Canceling it in the dashboard refuses the payment; an approval in the dashboard is not Mandate's and the payment stays unsettled. A hold is canceled at the first reconcile round (every 60 s) after nothing can approve it: for an open quote once its consent expired; for a confirm the desk journaled once its certificate expired and 60 s more passed; at once for a quote closed without money or unknown after a restart. While the bank cannot be reached the hold is kept. Holds are released only by a desk on the sandbox rail. `--two-step` needs `--rail sandbox`; without it `mandate-console` exits with `--two-step needs --rail sandbox`.

With `--ach`, a certified payment leaves as an ACH transfer, which Mandate counts as paid once the bank accepts it. Days later the bank settles it or returns it; each outcome is a new sealed registry entry linked to the payment, shown with the receipt in the explorer's `Bank lifecycle` panel. On the sandbox nothing reaches the Federal Reserve, so every return is one the operator triggered with `mandate-bank-simulate`, and Mandate labels it `SIMULATED RETURN` everywhere. Run `mandate-bank-setup --ach` once so the payee has an account number, and use `mandate-bank-simulate {submit,settle,return} <ach transfer id>` (`--reason` one of `insufficient_fund`, `account_closed`, `no_account`, `payment_stopped`) from a shell that holds the key. `--ach` needs `--rail sandbox` and cannot be combined with `--two-step`; `mandate-console` exits with `--ach needs --rail sandbox` or `--ach and --two-step are exclusive`.

Increase asks Mandate before it approves a purchase on the agent's card, and declines by itself if Mandate does not answer within 4 seconds. Mandate approves only a purchase that matches a quote the holder approved, through the same gate and certificate as every payment, and the bank's decision id becomes the payment id in the receipt. In the sandbox a purchase is a simulation run by the operator with the bank key (`mandate-card-charge`); the agent never holds the card number or the key. The webhook listens on its own loopback port so a tunnel exposes nothing else. An answer whose outcome is unknown keeps the holder's intent blocked in Mandate for good: the owner sees what the bank did in the Increase dashboard, and paying again needs a new holder intent. The bank key is read from `INCREASE_SANDBOX_API_KEY` and the webhook secret, which Increase signs every card webhook with, from `INCREASE_SANDBOX_WEBHOOK_SECRET`; `--card-webhook-port` needs `--rail sandbox` and cannot be combined with `--two-step`.

On the sandbox rail the holder can also prove their Increase balance over TLS. Build the tool once with `cargo build --release` in `zktls/` (TLSNotary `v0.1.0-alpha.14`; local only, CI never builds it), set `MANDATE_ZKTLS_BIN=zktls/target/release/mandate-zktls`, start `mandate-console --rail sandbox --state-dir ~/.mandate-demo --zktls`, sign the intent on the holder page, then run `mandate-holder-proof --desk http://127.0.0.1:<port> --intent <intent id>` in the holder's own shell. The holder's process runs a TLS session with `sandbox.increase.com` for `GET /accounts/<id>/balance`, with Mandate's notary taking part, and uploads a presentation that reveals the request line, its fixed headers (including `Connection: close`) and its `Mandate-Nonce` header (the intent hash), the response status and all response headers, and the response's `account_id` and `available_balance` fields; it hides the `Authorization` value and every other field of the answer. Mandate's verifier checks the notary signature, the server name, that the session is at most 300 s old, that the session holds exactly one request (asking the bank to close) and one response (its revealed `content-length` accounts for every received byte, so no second answer can supply the balance), the intent binding and the account, then reads the balance in the proof and checks that it covers the amount; the balance is the one at proof time, and the kept proof does not expire before the payment is confirmed; the receipt then names the proof as `ev:zktls-attestation:<digest>` instead of the cooperative statement. What this does not prove: the balance is seen by Mandate's verifier (no predicate proves `balance >= amount` without revealing it), and the notary is Mandate's own, so a third party is convinced only as far as it trusts that notary key. The holder key (`INCREASE_HOLDER_API_KEY`) is a second, unscoped sandbox API key, because Increase offers `read_only` scopes only to OAuth apps that exchange a production token; it is read only by `mandate-holder-proof`; `mandate-console` removes it from its own environment at start and never reads it. Before proving, `mandate-holder-proof` refuses a challenge that names any host but `sandbox.increase.com`, any path but `/accounts/<id>/balance`, other revealed fields, a nonce that is not 64 lowercase hex, or a notary that is not on loopback, and it refuses a desk URL that is plain `http` to another machine, so a desk cannot steer the holder key elsewhere. The explorer's last step, `Funds proof`, checks in the browser that the proof's reference and digest are bound to the certificate, not the TLS proof itself. Live tests: `pytest -m live e2e/test_zktls_live.py` (needs `MANDATE_ZKTLS_BIN`, `INCREASE_SANDBOX_API_KEY` and `INCREASE_HOLDER_API_KEY`).

Each registry seal is stamped through OpenTimestamps as its anchor digest, `sha256("mandate-anchor/v1:" ‖ gate public key ‖ the seal's signed bytes ‖ its signature)`, so a proof belongs to one desk's one seal even when two desks share a root. Stamping is off unless `mandate-console` is started with `--public-anchor`, because it sends the blinded digests to four public aggregators and asks Blockstream's Esplora for Bitcoin block headers; it needs `--state-dir` (without it the console exits with `public anchor needs --state-dir: proofs are upgraded hours later`), because a proof is upgraded hours later and must outlive the process. A seal is stamped within ten minutes (or on `POST /api/anchor`, body `{}`). The receipt carries the proof as `public_anchor`, and the explorer's `Public anchor` step shows `PENDING` until a Bitcoin block attests it, usually hours later. A round that a calendar or the block source kept from completing is logged at warning with its reason (for example `anchor round incomplete (anchor: 1 of 4 calendars answered)`), a round that raised is logged by its type only (`anchor round failed (<type>)`), and either is retried at the next one; the console keeps serving. `POST /api/anchor` answers `409 anchor busy` while a round runs, the background one included. A calendar answer the explorer could not read (an operation other than sha256, append and prepend, a repeated operation, nesting past 255 operations, or a proof over 32768 bytes) counts as no answer and is never stored.

Offline, the explorer recomputes that digest from the receipt's seal and the gate key, refuses a proof over anything else (a bare root, another desk's seal), and checks that the proof leads from it to the merkle root of the Bitcoin header in the receipt, and that the header carries real proof of work. Whether that block is in Bitcoin's main chain is checked at any block explorer: look the block up by the hash the `CONFIRMED` line prints, not by its height: the browser cannot tie the header to the height the proof names, and the hash names the exact header it checked.

To check without the explorer, with the reference client (`pip install opentimestamps-client==0.8.0`): save the receipt as `receipt.json` and extract the proof with `python3 -c 'import json,sys,base64; sys.stdout.buffer.write(base64.b64decode(json.load(open("receipt.json"))["public_anchor"]["ots"]))' > seal.ots`. `ots verify` needs the anchor digest, not the seal root, so first compute it with the gate key (`gate_key` from `/api/keys`, or the key you recorded for the run): `python3 -c 'import json,sys,base64,hashlib; r=json.load(open("receipt.json")); s=r["registry"]["seal"]; b=json.dumps([s["anchor_id"],s["root"],s["seq_from"],s["seq_to"],s["ts"],s["v"]],separators=(",",":")).encode(); print(hashlib.sha256(b"mandate-anchor/v1:"+base64.b64decode(sys.argv[1])+b"anchor/v1:"+b+base64.b64decode(s["signature"])).hexdigest())' <gate key from /api/keys>`. Then run `ots --no-bitcoin verify -d <anchor digest> seal.ots`. It prints the block height and merkle root to compare at any block explorer (it exits 1 even for a good proof, because it checked nothing against a node); with a local Bitcoin node, drop `--no-bitcoin`.

A confirmed anchor proves this gate's signed seal, and so its root, existed no later than that block's time. It says nothing about whether the entries are correct. Rekor and a public testnet transaction are alternatives this desk does not use.

The Mandate desk (`mandate-desk`) serves quote, status, confirm and receipt tools over MCP. Spark reaches it through an app-side bridge (`swarm/mcp_bridge.py`) because the Meta Responses API has no remote-MCP tool; Muse Code connects directly through `mcpServers`. Confirming a payment needs the holder's signed consent, which the gate verifies and consumes once. WebMCP runs on the glasses only in Developer Mode or rollout, and the glasses assistant can list and show a payment but cannot approve it: only the holder's tap on Approve signs.

To run the desk locally, start `mandate-desk` (after `pip install -e .`). It prints one line, `Pair the holder device: http://127.0.0.1:8765/app/#pair=<token>`. Open that URL once on the approving device: the page registers its holder key with the one-time token and removes it from the address bar. Each approval is signed by a fresh key that the paired key certifies, so the signature over a payment never names the paired key. Later visits use `http://127.0.0.1:8765/app/`. The `/api` and `/app` routes accept only `127.0.0.1`, `localhost` and `[::1]` as Host; pass `--public-host <name>` to add the name of an HTTPS proxy in front of the desk. On `mandate-console`, the console routes (`/api/lines`, `/api/events`, `/api/forensic/<seq>`) show every payment's amount, payee, reference and debit account in clear to anyone who can reach a `--public-host` name, so a public host is for demo data only.

`mandate-console --holders N` (default 1, at most 16) prints one pairing URL per device, `Pair the holder device: http://127.0.0.1:8766/app/#pair=<token>`; each URL pairs one device, once, and up to 16 holders pair at once. Each pairing link works once and only for ten minutes after the console starts; restart the console for a new one. Each holder approves only its own payments: a payment that starts from a holder-signed intent belongs to the intent's signer, and an open quote without one belongs to the first holder whose approval the desk accepts. `Unpair this device` on the glasses page retires that device's key for good: it never pairs again, and the receipts it approved keep verifying. With `--state-dir`, holders survive restarts; the console lists them as `Holder <id>: device <fingerprint>` on its own terminal only, and `--unpair <id>` (repeatable) retires one before serving. For a demo with several holders, run `mandate-console --holders 3 --state-dir ~/.mandate-demo`, open each printed URL on its own device (the glasses, a phone, a second browser profile) and give each holder its own invoice reference; the explorer then reads `Anonymity set: 3 holder keys`. That set hides which holder approved a receipt from its readers, not from the gate or its operator, which bind every payment to one holder.

While a payment waits, the console's holder approval panel shows the seven consent fields the holder's device signs, the sha256 of those bytes (the holder page shows the same grouped hash under `Consent hash`), how many holder devices are paired (`GET /api/device`; each holder page shows its own device as `This device <fingerprint>`), and the outcome through to the booth. The console holds no key and cannot approve. Verify with `cd console && npm run e2e`; the panel's states (refused, expired, approved, paid, gate mismatch, denied, desk unreachable, no WebCrypto, replay) are captured by `console/e2e/approval-states.spec.ts` with `CAPTURE=1 npx playwright test e2e/approval-states.spec.ts`.

With `--voice` (on `mandate-desk` or `mandate-console`), the holder page can record a spoken confirmation: tap `Speak to confirm`, say the payment, tap `Stop`. The desk forwards the clip once to Muse Voice Transcribe and returns only the words, which the page shows under the seven consent fields with the line `Voice is a confirmation, not proof of who spoke. Only your Approve tap signs, on this device.` The desk transcribes only a clip the paired device signed (`x-mandate-voice-sig`), keeps no audio and never signs; the words never enable or block Approve. The microphone needs https or localhost. The desk reports on `GET /api/device` whether `--voice` is on; with it off the page hides `Speak to confirm` and never asks for the microphone. Each signed clip is transcribed once per pending quote, a quote past its deadline is refused, and a second upload is refused before its body is read.

The reasoning anchor (`swarm/anchor.py`, checked by `e2e/test_anchor_live.py`) binds a certificate to the model, response id and encrypted reasoning that Meta returned, so it proves non-substitution after issuance; Meta Model API does not authenticate replayed encrypted reasoning, so it does not prove that Meta re-verified the reasoning. The attacker row counts as open weights only when its recorded provider reads `baseten`; an attacker that fell back to the Meta Model API is labeled `meta-fallback`. The attacker model fills the parameters of seven fixed attack templates, and each plan is applied deterministically through the real defense layer it targets.

The console shows what the gate decides as it happens. Build it with `cd console && npm ci && npm run build`, then run `mandate-console` (after `pip install -e .`); it prints the pairing URL and `Console: http://127.0.0.1:8766/console/`. `POST /api/attack {"kind": ...}` runs one of seven pinned template attacks (no model call), and the ledger labels it `TEMPLATE`. `--journal <state-dir>/journal.jsonl` streams Muse Code hook decisions into the same ledger. `--record run.jsonl` captures the stream of one process; use a fresh file per run, because a capture whose line numbers start over is refused. A capture copied to `console/public/replay/<name>.jsonl` plays at `/console/?replay=<name>` under a permanent `REPLAY` label after `npm run build` and a restart of `mandate-console`, which serves the build it found at startup. Verify with `cd console && npm run e2e`.

`/console/holder.html` on the desk's origin is the holder's device page; it shares the `/app/` page's paired key. Type or record the payment, check the fields Muse Spark drafted against the payee book (`--payees`, default `demo/payees.json`), and sign on the device. The page then shows the intent id, its hash and the bank's funds statement, verified in the browser. `Hand to Muse Spark` gives the agent only the intent id: it quotes, the holder approves on `/app/`, and it confirms. Without `MODEL_API_KEY`, drafting and the handoff say Muse Spark is not configured. Clips over 10 minutes or 31,000,000 bytes are refused on the device. Verify with `cd console && npm run e2e` and `pytest -m live e2e/test_mcp_live.py`.

Open http://127.0.0.1:8766/console/command.html next to the live console for the posture view: every number is computed from the console's lines, each metric states its definition and lists the lines behind it, and Export writes a Markdown or JSON report with the window, registry root and policies it rests on. The framework table maps Mandate controls to NIST AI RMF, ISO/IEC 42001 and EU AI Act provisions; it is not a certification or a statement of compliance.

The ATTACK button in the top bar opens the attack panel. It has seven pinned template attacks (labelled `TEMPLATE`; the same press runs the same attack and is denied with zero cents moved); the seventh forges the holder's approval, signed by a key that is not the paired holder's, and dies at the gate's consent check), and the three Nimbus deploy steps (labelled `SCENARIO`). `mandate-console --live-attacker` also enables a control that asks an open-weights model to plan the attack; it is off by default, needs `BASETEN_API_KEY`, and otherwise falls back to the Meta API with `MODEL_API_KEY` or `META_API_KEY`, labelled as not open weights. Without the flag the control is disabled and says so. Opening the forensic drawer of a denied line offers KILL-CAM, a tape that replays step by step which check refused it; it is rebuilt from the line's forensic record and nothing is run again.

`POST /api/deploy {"step": "release" | "poisoned_tool" | "stale_migration"}` runs one pinned Nimbus step through the gate, the MCP proxy and a simulated prod-eu target (no model call). The console's right-hand world shows Nimbus HQ for deploy and Muse Code hook lines and the bank for payment lines, and the BRANCH / NIMBUS HQ toggle shows either while the booth is idle.
