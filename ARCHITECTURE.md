## Invariants (non-negotiable)
1. Enforce at the execution boundary (gate + resource server), never in the prompt.
2. The agent never holds the mother credential — only ephemeral, strictly-scoped delegations.
3. The agent never enters the bank session; humans prove state client-side; the agent sees receipts only.
4. Total determinism on the decision path; no LLM votes in the gate; uncheckable input yields NOT CHECKABLE, never a guess.
5. Everything verifiable by third parties without exposing secrets.
6. Zero honeypot: store receipts and hashes only — never statements, sessions, or secrets.

## What a certificate binds
The action hash is HMAC-SHA256 (RFC 2104) over the canonical action bytes, keyed by a fresh 32-byte random salt the gate draws for each decision. The certificate, the decision event, the console line, the bank's payment record and a deploy release all carry this one value. The certificate binds this salted hash, so a certificate cannot be used to confirm a guessed amount, payee, reference or account. The salt goes to the bank verifier (in process, beside the action it must pay). The desk keeps it with the payment's private record and never publishes it: it is in no console line, event, registry entry, MCP tool result or `receipt()` output. It is meant to be disclosed only in the holder's copy of the receipt. That copy will be served by the proof explorer, which is not built yet, so today no one outside the process can recompute a certificate's action hash.

The certificate's scope names the operation only (`mcp:bank.pay:transfer`). The debit account is bound through the `from:` target inside the hash, the holder's consent and the bank's exact-action check.

The hook journal, the MCP proxy and the frozen-approval payload keep an unsalted SHA-256 because their records carry the action in clear and issue no certificate.

What stays visible: payment ids are sequential; a consent carries only its per-payment key and the paired key's certificate over that key and the nonce, so receipts built from consents (the holder copy served by the proof explorer, not built yet) will not carry the paired key and will keep that certificate concealed (a signature by the paired key lets anyone holding a candidate key test it), so an outsider will not be able to link two of them to one holder; an issuer and a verifier that collude can recognise a receipt (RFC 9901 section 10.1).

What can still be linked: the gate and whoever operates the desk know which paired key certified every consent. A desk with one paired holder makes every receipt it issues that holder's, so the anonymity set is the holders paired with one gate. Payment ids, quote ids and timestamps are sequential. The bank links payments by the debit account it debits. A disclosed field links by its value (RFC 9901 section 10.1).

Console lines and `--record` files show the action in clear. They are operator-only material, never auditor material.

## Honest seams
- Reasoning anchor (swarm/anchor.py): binds a certificate to the model, response id and encrypted reasoning that Meta returned. Meta Model API does not authenticate replayed encrypted reasoning, so the anchor proves non-substitution after issuance, not that Meta re-verified the reasoning.
- Muse Code subagent scope (swarm/hook.py): authority (manifest, state, keys, journal) lives outside the governed workspace and is pinned via the hook's argv (`mandate-hook --state-dir <abs> --root <abs>`); nothing under the repo is read as authority, event cwds must be the repo root or a worktree under `.muse/worktrees/`, and file-tool writes under `.mandate/` and `.muse/` are refused and shell tokens (including fragments split at every `=` and `:`) that name `.muse` or `.mandate` or escape the worktree are refused, which also denies URLs in shell commands (fail closed). Read tools may still read `.muse/` and `.mandate/` inside the worktree, since authority lives outside it. File atoms are checked exactly, shell atoms only by the first binary of each command segment, and token checks do not see paths that an executed program constructs; code executed by an allowed binary (pytest, git) is contained by Muse Code's OS sandbox and worktree isolation, not by Mandate.
- Red-team attacker (swarm/redteam.py, swarm/attacker.py): the model fills the parameters of seven fixed attack templates; each plan is applied deterministically through the real defense layer it targets. Replay takes no parameters, and the scope-escalation and MCP-exfil kinds are checked at their own layer without touching the bank. The forged-approval kind (`forged_approval`) runs through the desk's consent rule against the console desk's in-memory demo bank, with a holder key minted per press, and dies at the gate's consent check.
- Holder consent (gate/consent.py): when a rule sets `consent_required`, the holder's device signs pinned bytes binding amount, currency, payee, reference, debit account, nonce and expiry with an Ed25519 key drawn for that consent alone, and the paired holder key certifies that key for the consent's nonce (consent-key/v1); the gate verifies both signatures, refuses a key among the last 100,000 it consumed in this process (the key ledger is in memory, bounded, evicts first-in first-out in step with the nonce ledger, and is lost on restart) or a paired key used directly (consent: key reused), and consumes the nonce and the key once. Voice intents (swarm/intent.py) are signed but are not yet gate-verified consents. The holder key is provisioned once: `mandate-desk` prints a one-time pairing token locally, and `POST /api/holder` registers a key only with that token, which is spent on first use; a restart issues a new token and forgets the holder. The `/api` and `/app` routes refuse a Host outside `127.0.0.1`, `localhost` and any `--public-host` names, so a DNS-rebound page cannot drive them. Desk state is in memory, and revocation indices wrap at 1024.
- Console (swarm/console.py, console/): attacks started from the console are deterministic templates and are labeled `TEMPLATE`; the replay template pays the legitimate 200.00 once per click before replaying its certificate. Console state is in memory and line numbers restart with each process, so clients restart from zero when the stream announces a new epoch. The journal tail publishes only hook records under the `hook` source; anything else in the journal, including a console line claiming another source, is skipped. Replay mode (`?replay=<name>`) plays a recorded stream and says `REPLAY` for as long as it is active.
- Attack panel routes (swarm/server.py, swarm/live_attack.py): `GET /api/attack` lists the pinned templates and whether the live attacker is available; `POST /api/attack/model {"kind"}` asks the open-weights attacker (`swarm/live_attack.py`) for a plan, one request at a time, and publishes a line only when the reply yields a plan that the gate then decides. The live attacker exists only with `--live-attacker`; templates never call a model. The kill-cam is built in the browser from the forensic block of the line, so it adds no route.
- Nimbus deploy (swarm/nimbus.py): steps are pinned and labelled `SCENARIO`; prod-eu is simulated and verifies the release certificate offline. The Nimbus policy names the current migration, so a superseded one matches no rule. The release intent carries no money because deploy rules never read it. A live Muse Code deploy is governed by the hook's cmd atoms, which see only the first binary of each shell segment.
- Holder approval panel (console/src/approval/): the hash it shows is the consent hash (sha256 of the seven signed consent fields), not the action hash; the canonical action and its hash exist only at confirm and appear in the forensic drawer. Device state (`GET /api/device`) is pairing only, not liveness: the desk cannot tell whether the paired device is watching. Local expiry is shown on the console's clock and enforced only by the desk and the gate.
- Voice confirmation (swarm/voice.py, swarm/server.py, webapp/app.js): the transcript is a displayed confirmation, never compared with the consent fields and never an authority; push-to-talk mode (`PUSH_TO_TALK`) returns no speaker attribution. The clip leaves the device for the desk and Meta and is not stored. Voice spend is limited to the paired device: `POST /api/voice` transcribes only a clip whose `mandate/voice/v1` signature (quote id and sha256 of the received body) verifies against a paired holder key, checked before any model call, one call at a time (a second upload is refused before its body is read), each signed clip once per pending quote, never for a quote past its deadline, and only on a desk started with `--voice`; `GET /api/device` reports that flag so the holder page offers the microphone only when it is on. The holder page also sends `frame-ancestors 'none'`. That signature authenticates the uploading device, not the speaker, and is never a consent.
- Spawn binding assumes children are created only through subagent_spawn: SubagentStart carries no parent id, so the next UUID child claims the single pending spawn.
