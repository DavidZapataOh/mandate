## Invariants (non-negotiable)
1. Enforce at the execution boundary (gate + resource server), never in the prompt.
2. The agent never holds the mother credential — only ephemeral, strictly-scoped delegations.
3. The agent never enters the bank session; humans prove state client-side; the agent sees receipts only.
4. Total determinism on the decision path; no LLM votes in the gate; uncheckable input yields NOT CHECKABLE, never a guess.
5. Everything verifiable by third parties without exposing secrets.
6. Zero honeypot: store receipts and hashes only — never statements, sessions, or secrets.

## What a certificate binds
The action hash is HMAC-SHA256 (RFC 2104) over the canonical action bytes, keyed by a fresh 32-byte random salt the gate draws for each decision. The certificate, the decision event, the console line, the bank's payment record and a deploy release all carry this one value. The certificate binds this salted hash, so a certificate cannot be used to confirm a guessed amount, payee, reference or account. The salt goes to the bank verifier (in process, beside the action it must pay). The desk keeps it with the payment's private record and never publishes it: it is in no console line, event, registry entry, MCP tool result or `receipt()` output. It appears only in the holder copy of the receipt (`GET /api/receipt/<id>?disclose=all`, served only to a loopback client with no proxy headers), as the `action_salt` Disclosure beside the action's targets. The auditor copy withholds it, so no one holding only that copy can recompute the action hash.

The certificate's scope names the operation only (`mcp:bank.pay:transfer`). The debit account is bound through the `from:` target inside the hash, the holder's consent and the bank's exact-action check.

The hook journal, the MCP proxy and the frozen-approval payload keep an unsalted SHA-256 because their records carry the action in clear and issue no certificate.

What stays visible: payment ids are sequential; a consent carries only its per-payment key and the paired key's certificate over that key and the nonce, so a receipt built from a consent carries the one-time key in clear and keeps the paired key and its certificate (the `holder_key` and `key_signature` Disclosures) concealed unless the holder discloses them (a signature by the paired key lets anyone holding a candidate key test it, and `/api/keys` publishes the paired keys), so an outsider cannot link two receipts to one holder; an issuer and a verifier that collude can recognise a receipt (RFC 9901 section 10.1).

What can still be linked: the gate and whoever operates the desk know which paired key certified every consent. To a reader of receipts, the anonymity set of a receipt is the set of holders paired with the gate that issued it (the explorer states its size from /api/keys, which lists every key that ever paired, including keys unpaired since, so the set can be larger than the holders paired when that receipt was approved); with one paired holder, every receipt is that holder's. Payment ids, quote ids and timestamps are sequential. The bank links payments by the debit account it debits. A disclosed field links by its value (RFC 9901 section 10.1).

## What a receipt reveals
A receipt is an SD-JWT (RFC 9901) signed by the gate. The gate signs salted digests of the personal fields; a copy carries only the Disclosures its holder chooses to send. Two copies exist.

| Field | Auditor copy (`/api/receipt/<id>`) | Holder copy (`?disclose=all`) |
| --- | --- | --- |
| Payment id, quote id, policy, rule, matched certificate, registry entry, inclusion proof, seal, timestamps | readable | readable |
| Action kind (`bank.pay`, `transfer`, `payments`), `reversible`, freshness nonce | readable | readable |
| Reasoning anchor (model, response id, commitment, Meta's encrypted blobs) | readable | readable |
| Consent nonce, expiry and the one-time consent key (fresh per payment) | readable | readable |
| Amount and currency, payee account, reference, debit account | withheld | readable |
| Action targets and the action salt | withheld | readable |
| Consent signature | withheld | readable |
| Paired holder key and its certificate over the one-time key | withheld | readable |
| Bank transfer (`bank`): rail, provider, transfer id, status and idempotency key (`mandate-cert-<jti>`), gate-signed inside the SD-JWT payload; never the API key or a balance | readable | readable |
| Funds proof (`funds`), gate-signed inside the SD-JWT payload and always visible: the funds kind (`cooperative` or `zktls`), its evidence reference (also in the certified `evidence_refs`), and for zkTLS the presentation digest, server name, session time and notary key; never the balance, the bank account id or the cooperative statement itself | readable | readable |
| Public anchor (`public_anchor`), unsigned, the OpenTimestamps proof of the seal's anchor digest (blinded sibling digests and calendar URLs), plus the Bitcoin block header once confirmed | readable | readable |

A holder who shares a receipt ticks the groups an auditor may see (amount, payee, account, reference, holder identity); the explorer drops the other Disclosures without re-signing, and the gate's signature still covers their digests. The targets, the action salt and the consent signature travel only with all four field groups, because each of them would let a reader confirm a guess about a hidden field. The holder group is independent: its certificate covers only the one-time key and the visible nonce, so it confirms no withheld field and only names the paired key that approved.

Routes below are `GET`, JSON, behind the Host allowlist (`127.0.0.1`, `localhost`, `[::1]` and any `--public-host` name; a foreign Host gets 400) and with no CORS headers, so only the console origin reads them:

- `/api/keys` publishes the gate public key and every holder public key that ever paired, in pairing order (unpaired keys stay listed so the receipts they approved keep verifying). Nothing private.
- `/api/registry` publishes the latest signed registry seal.
- `/api/receipt/<id>` is the auditor copy. `/api/receipt/<id>?disclose=all` is the holder copy and is served only when all three hold: the connecting client is loopback (`127.0.0.1`, `::1` or `::ffff:127.0.0.1`), the request Host is loopback (`127.0.0.1`, `localhost` or `[::1]`, any port, any case), and the request carries none of `Forwarded`, `X-Forwarded-For`, `X-Forwarded-Host`, `X-Forwarded-Proto`, `X-Real-IP` or `CF-Connecting-IP`. Anything else, including a `--public-host` name, gets 403 `holder copy is local only`. Any other query is a 400, an unknown id a 404.
- `/api/receipt/by-hash/<hash>` is the auditor copy of the receipt whose receipt hash (SHA-256 of the gate-signed JWT that opens the receipt's SD-JWT, the same in every copy) or certified action hash is `<hash>`. Only a whole 64-character lowercase hex hash is looked up: anything else, or any query parameter, is a 400. A hash no receipt has is a 404, and so is a registry leaf hash: every inclusion proof carries a neighbour's leaf as a sibling, and resolving it would hand the neighbour's receipt to whoever holds this one. The holder copy is never served by hash. On the sandbox rail the payment id is the bank's transfer id, so `/api/receipt/<transfer id>` finds the same receipt.

`POST /api/anchor` runs one stamp and upgrade round when the console was started with `--public-anchor`.

The local-only rule keeps a public auditor from fetching the holder copy, which would defeat the salted action hash and the concealed paired key. The Host header alone proves nothing (a client sets it), so the desk also requires a loopback peer address, and it refuses any request that names a proxy, because a proxy on the same machine connects from loopback. The rule is not authentication: anyone who can open a loopback connection to the desk gets every holder copy, and payment ids are sequential. A proxy that strips every forwarding header and relays from loopback still defeats it, so never front the desk with one. A remote holder pastes their copy into the explorer instead.

What never leaves the desk: the gate's and the holder's private keys, account balances, the bill behind a payment, and the model's reasoning in clear (a receipt holds only its commitment and Meta's encrypted blobs). Two regression tests pin the receipt: one fails if either private key appears in it in base64 or hex, the other fails if it names another payment's reference or id. A receipt reaches its neighbours only as sibling hashes in the inclusion proof.

What this does not hide:
- The gate and whoever operates the desk know which paired key certified every one-time key; the anonymity set hides the holder from readers of receipts, not from the gate. A gate with one paired holder issues every receipt for that holder.
- The bank links payments by the debit account it debits.
- Payment ids, quote ids and timestamps are sequential. Anyone who can reach the console origin can enumerate auditor copies, and each shows the registry entry's payment and quote ids. The demo desk binds to localhost (or a named `--public-host`); a production desk hands the holder copy only to the holder.
- A disclosed field links by its value: the same payee account or reference in two copies is the same value.
- An issuer and a verifier that collude can recognise a receipt whatever is disclosed (RFC 9901 section 10.1).
- The paired keys are published at `/api/keys`, so an auditor who is given a holder's `key_signature` can confirm which published key approved.

A withheld field cannot be confirmed by guessing: the certificate's action hash is HMAC-SHA256 keyed by the concealed action salt, its scope names no account, and the one-time key's certificate stays with the paired key's Disclosures.

Console lines and `--record` files show the action in clear. Nothing restricts them to the operator: the console routes (`/api/lines`, `/api/events`, `/api/forensic/<seq>`) answer on every allowed Host, so with `mandate-console --public-host <name>` anyone who reaches that name reads every payment's amount, payee, reference and debit account in clear, and the explorer's withheld fields are withheld only from the receipt. A public host is for demo data only.

## Funds proof over TLS (zktls/)
On the sandbox rail the holder can replace the cooperative funds statement with a TLSNotary (`v0.1.0-alpha.14`) proof of their own Increase balance. One binary, `mandate-zktls`, plays three roles in three processes:

```
 holder's shell                          mandate-console (desk)
 ---------------------------             --------------------------------------
 mandate-holder-proof                    POST /api/intent/funds-challenge
   holds INCREASE_HOLDER_API_KEY   <---    host, path, nonce = intent hash,
   |                                       notary address and key, fields
   | mandate-zktls prove                 mandate-zktls notary (child process)
   |   MPC-TLS session  <-------------->   127.0.0.1:7047, secp256k1 key drawn
   |        |                              at console start, never stored
   |        v                                     |
   |   sandbox.increase.com:443               signs the attestation
   |   GET /accounts/<id>/balance                 |
   v                                              v
 presentation (account_id and      --->  POST /api/intent/funds-proof
 available_balance revealed,             mandate-zktls verify (child, 30 s)
 Authorization hidden)                     Mozilla roots, notary signature
                                         evidence/zktls.check_balance
                                           notary key, server, <= 300 s,
                                           one request (connection: close),
                                           one response (head revealed,
                                           content-length = the rest),
                                           account, nonce, 200,
                                           balance covers the amount
                                         intent funds ref := ev:zktls-attestation:<sha256[:32]>
```

Trust boundary: the holder key stays in the holder's process and reaches the prover by name (`--auth-env`), and the holder CLI runs the prover only for the pinned host, path, fields, nonce form and a loopback notary; the presentation carries the `Authorization` header name with its value hidden. The desk's side holds the notary key and runs the verifier, and it sees the account id and the balance in the clear; the balance stays in the desk's memory and is reduced to "covers the amount". The proof is only as strong as Mandate's notary key, because Mandate both notarizes and verifies. The browser never sees the presentation: the receipt's gate-signed `funds` view carries its digest, server name, session time and notary key, and the explorer's `Funds proof` step checks that this view matches the certified `evidence_refs`. The verifier runs outside the desk lock, and the intent is checked again before the proof is kept.

## Honest seams
- Reasoning anchor (swarm/anchor.py): binds a certificate to the model, response id and encrypted reasoning that Meta returned. Meta Model API does not authenticate replayed encrypted reasoning, so the anchor proves non-substitution after issuance, not that Meta re-verified the reasoning.
- Muse Code subagent scope (swarm/hook.py): authority (manifest, state, keys, journal) lives outside the governed workspace and is pinned via the hook's argv (`mandate-hook --state-dir <abs> --root <abs>`); nothing under the repo is read as authority, event cwds must be the repo root or a worktree under `.muse/worktrees/`, and file-tool writes under `.mandate/` and `.muse/` are refused and shell tokens (including fragments split at every `=` and `:`) that name `.muse` or `.mandate` or escape the worktree are refused, which also denies URLs in shell commands (fail closed). Read tools may still read `.muse/` and `.mandate/` inside the worktree, since authority lives outside it. File atoms are checked exactly, shell atoms only by the first binary of each command segment, and token checks do not see paths that an executed program constructs; code executed by an allowed binary (pytest, git) is contained by Muse Code's OS sandbox and worktree isolation, not by Mandate.
- Bank key (bank/credentials.py, swarm/console.py): only the process that holds the bank verifier holds the Increase key. `mandate-console --rail sandbox` pops `INCREASE_SANDBOX_API_KEY` from its own environment before doing anything else, so no process it spawns inherits the key, and `mandate-hook` refuses every tool call when its environment holds an Increase key under any of the names in `BANK_KEY_NAMES` (`INCREASE_SANDBOX_API_KEY`, `INCREASE_HOLDER_API_KEY`, and `INCREASE_API_KEY`, which the SDK reads); `without_bank_key` drops all three from an agent's environment. The console process's initial environment is still readable by other processes of the same user on macOS (`ps -E`), and that includes `INCREASE_HOLDER_API_KEY` if the console was started with it, although it pops that key too; passing the key through a file or stdin would close that.
- Bank outcome (bank/increase.py, bank/verifier.py, swarm/desk.py): the verifier consumes the certificate before it calls the bank, once, under the idempotency key `mandate-cert-<jti>`. Because the jti is spent first, a transfer the bank holds under that key on the certificate's first presentation can only be this certificate's own: an answer Increase marks `Idempotent-Replayed: true` (the SDK resending after a lost response) is compared field by field with the request (amount, currency, source and destination account ids, idempotency key) and paid when it matches and is `complete`. Every transfer answer gets the same comparison; a mismatch is the refusal `bank: transfer differs`, recorded and never paid, and since something exists under the key it leaves the bound intent unsettled too. A second presentation of the same certificate still dies at `replay: jti consumed` before the bank, and a key reused with other parameters (409) is `replay: bank idempotency key`. The client never follows a redirect. When the transfer call gets no usable answer (timeout, connection error, 3xx, 5xx, a 4xx whose error body does not parse, or a 2xx that is not a transfer, such as HTML, unparsable JSON or a list), the rail makes one lookup, `GET /account_transfers?idempotency_key=<key>`: a matching complete transfer is paid, one not yet complete is `bank: not complete`, and none (or no answer to the lookup, or one that is not a list of transfers) is `bank: outcome unknown`. Only a 4xx with a parsed error is a definite refusal. If paying a bound intent fails in any other way the desk did not expect, it treats the outcome the same: the quote is denied `bank: outcome unknown` with a sealed denial, the intent becomes unsettled under the key its certificate carries, and the log names only the exception type. After `bank: outcome unknown`, `bank: not complete` or `bank: transfer differs` the bound intent is `unsettled`: its receipt says so and names the key, and confirming any new quote for it is refused `intent: unsettled` (a sealed denial, no bank call). The holder's next hand-off to the agent first looks the key up again (`PaymentDesk.reconcile_intent`): a matching complete transfer spends the intent (with a state directory it is settled from the journal as below, with a sealed execution entry and a receipt; without one the quote that sent it becomes confirmed with `ok: reconciled` and an execution entry is sealed, without a proof receipt). A differing transfer is never paid and never released: the holder's sentence says the operator must check it at the bank. A lookup that finds nothing releases the intent for a new quote only once its certificate has expired (300 s after the confirm's start, before the bank call, on the desk's clock) and `SETTLE_WINDOW_S` (60 s) more have passed; earlier the intent stays unsettled and the holder is asked to try again later, because a transfer whose answer was lost may still be committing or not yet listed. With a state directory that release is the journal's sealed `bank: no transfer under this certificate`. A lookup that cannot tell leaves it unsettled. Without a state directory, unsettled state lives in the desk's memory and is lost on restart: after a restart the desk no longer knows that a key is open. With one, the intent stays unsettled across a restart and its journal is settled by the reconciler (below). Without a state directory, a transfer that Increase lists only after that release is not caught; with one, it is reported as a second payment of the intent (below). Bank time is bounded because the desk holds its lock through the call: the client waits at most 5 s to connect and 10 s for each read or write, retries nothing on its own (the SDK would honour a Retry-After of up to 60 s), and a payment makes at most two calls (the transfer and one lookup, or the transfer and one balance read when Increase refuses it), so it gives up in about half a minute.
- Hold at quote (swarm/desk.py, bank/increase.py): on a desk whose rail holds transfers for approval, each quote is held at the bank as a transfer in `pending_approval` under `mandate-cert-<jti>`, the certificate's id drawn at quote time. The hold is the one bank write made before a certificate exists, so a quote is refused before any bank call when it names no intent (`intent: missing`), when its amount, currency, payee or reference differ from the intent's (`intent: differs`), when the intent already holds a transfer at the bank (`intent: held at the bank`), or when the intent already paid (`intent: already used`) or is unsettled (`intent: unsettled`). The desk stores a hold record before the call and keeps it unless the bank definitely refused (`bank: unavailable`, `bank: refused`, `denied: insufficient funds`, `denied: unknown account`). The call runs under the desk lock and makes at most two bank calls (the hold and one lookup), so it gives up in about half a minute. Each reconcile round first cancels every hold nothing can approve any more (outside the desk lock, re-checked under it): a journaled certificate's hold once the certificate expired and the 60 s settle margin passed; with no journal, an open quote's hold once its consent expired, and at once a hold whose quote closed without money or is unknown after a restart. A hold whose quote was confirmed is dropped with no bank call. A canceled hold is dropped (`<quote id> -> hold canceled`); a key the bank holds nothing under is dropped once the consent expired and 60 s more passed (`<quote id> -> no hold at the bank`); a hold the bank completed stays, blocking its intent, until it is sealed as the certificate's payment; otherwise it is counted unbacked. A transfer still in `pending_approval` under a key the desk holds is left out of the comparison, since it moved no money. A transfer approved by a person in the dashboard (`bank: approved outside the gate`) is never sealed as the certificate's payment: its journal stays pending and its intent unsettled.
- Two-step at the bank (swarm/console.py, bank/increase.py, bank/reconcile.py): `mandate-console --rail sandbox --two-step` holds every quote. The hold moves no money but holds funds, at most one per holder intent. It is canceled at the first reconcile round after nothing can approve it: once its consent expired for an open quote, once its certificate expired and 60 s more passed for a journaled confirm, at once for a quote closed without money or unknown after a restart. It is kept while the bank cannot be reached, and a hold the bank completed is a payment (sealed when it is the certificate's, unbacked otherwise), never canceled. The reconciler cancels holds and makes no other bank write. A hold whose transfer id the bank returned is read by that id when it is released, so a listing by key that omits it cannot drop it. Holds are released only by a desk on the sandbox rail: a desk started on the simulated rail over a store with sandbox holds keeps them and keeps their intents blocked, and the funds stay held at Increase until a sandbox desk runs again. A hold the bank completed with no certificate is read again every round; it stays for good, blocking its intent. An approval through any API key of the account reads as Mandate's, because Increase names only dashboard users in `approved_by`. A certificate replayed after a restart is a bank replay, never a second transfer.
- Funds statement on the sandbox rail (swarm/desk.py): the statement is signed by the desk's statement key over the balance the rail reports. On the sandbox rail that balance is Increase's `available_balance` and Increase signs nothing, so the holder page says the desk signs the statement over the balance its bank reports, which is true on both rails.
- Red-team attacker (swarm/redteam.py, swarm/attacker.py): the model fills the parameters of seven fixed attack templates; each plan is applied deterministically through the real defense layer it targets. Replay takes no parameters, and the scope-escalation and MCP-exfil kinds are checked at their own layer without touching the bank. The forged-approval kind (`forged_approval`) runs through the desk's consent rule against the console desk's in-memory demo bank, with a holder key minted per press, and dies at the gate's consent check.
- Holder consent (gate/consent.py): when a rule sets `consent_required`, the holder's device signs pinned bytes binding amount, currency, payee, reference, debit account, nonce and expiry with an Ed25519 key drawn for that consent alone, and the paired holder key certifies that key for the consent's nonce (consent-key/v1); the gate verifies both signatures, refuses a key among the last 100,000 it consumed in this process (without a state directory the key ledger is in memory, bounded, evicts first-in first-out in step with the nonce ledger, and is lost on restart; with one, nonces and keys stay on disk until their consent expired) or a paired key used directly (consent: key reused), and consumes the nonce and the key once. Holder intents are signed on the device and verified by the desk with the registered holder key. A quote that names one is checked against it at the gate (amount, currency, payee, reference), and each intent pays once. A quote that names none is checked against the holder's consent only, unless the desk requires intents (`require_intent`, used for the real bank rail), where it is refused `intent: missing` before the gate. The funds proof is a cooperative statement the desk signs over the balance its bank reports, with the intent hash as nonce; it is verified in the holder's browser and referenced by a hash over the statement and the bank's signature, so the reference does not reveal the balance. On the sandbox rail the holder can prove the Increase balance over TLS through Mandate's own notary (zktls/); Mandate's verifier sees the balance (no predicate proof); the browser checks only the binding; otherwise the funds proof is the cooperative statement. Drafting sends the holder's words to Muse Spark, and the paying agent receives only the intent and quote ids. The bank key comes from the same process as the desk. The holder key is provisioned once: `mandate-desk` prints a one-time pairing token locally, and `POST /api/holder` registers a key only with that token, which is spent on first use; a restart issues a new token, and forgets the holder unless a state directory keeps it. Several holders may be paired (at most 16, each through its own one-time pairing token printed to the operator); every quote is bound to one holder, and the gate receives only that holder's key at confirm. The `/api` and `/app` routes refuse a Host outside `127.0.0.1`, `localhost`, `[::1]` and any `--public-host` names, so a DNS-rebound page cannot drive them. Without a state directory, desk state is in memory.
- Durable state (gate/state.py, bank/reconcile.py): with `--state-dir`, one SQLite file (`state.db`, WAL, `synchronous=FULL`, mode 0600, in a 0700 directory locked to one process by its `lock` file) holds the registry entries and their seals, every receipt and confirm result, the spent certificate ids, consent nonces and one-time consent keys (each kept until it expired, which is safe because the gate refuses an expired certificate or consent before it reads the fence), the holder intents and their single use, the paired holders (paired and unpaired, under their opaque ids), the quote counter (so revocation indices count on across restarts), the simulated ledger's balances, payments and idempotency keys, and the latest reconciliation. The gate key is a separate 0600 file, `gate.key`, beside it. The database is holder-private too (every holder copy and every journaled certificate), so it is not an audit artifact: an auditor gets auditor copies. Start refuses a directory, database or key file that is a link, belongs to another user, or is open to group or others. On load the registry checks every stored entry against its seals, requires the newest seal to cover every entry (each append is sealed in the same transaction, so an unsealed tail means something else wrote the file), and refuses a store that does not match; a stored intent, result or journal that does not parse stops the start with `state: store unreadable`. The in-memory structures stay the decision path; each change writes through inside the desk's lock, and a confirm is one transaction around the registry append, the seal, the receipt and the dropped journal. Not durable, on purpose: open quotes (a restart voids them; their consent nonces were never spent, so the holder quotes again), the console window and its line numbers, the per-start funds statement and notary keys (nothing later verifies with them), open funds challenges, and the template attacks, which verify against an in-memory verifier and a simulated bank of their own, so their counted nonces never touch the durable fences.
- Write-ahead journal and reconciliation (swarm/desk.py, bank/reconcile.py): after the gate signs a certificate and before the bank is called, the desk stores the certificate, the action, its action salt and the consent as a pending record, and drops it once the outcome is known. A timeout (`bank: outcome unknown`) or a crash leaves it in place, and the reconciler settles it by looking the certificate's idempotency key up at the bank: a complete transfer becomes an ordinary sealed execution entry (`ok: executed`, after the earlier denial entry, append-only), a receipt and a desk `confirm` line with `ok: reconciled at the bank`; no transfer once the certificate expired and a 60 s settle margin passed becomes a sealed denial, `bank: no transfer under this certificate`, which releases the intent; a transfer the bank still holds for approval waits. It then lists every transfer from the debit account since the registry's genesis (`GET /account_transfers`, every page; its only bank write is the cancel of a hold, see Hold at quote) and counts as unbacked any transfer, other than a canceled one, whose idempotency key does not name a certificate this desk issued or whose receipt's entry is not the registry's; sealed payments the bank does not list, or lists as canceled, are reported as missing. It runs at start, every 60 s on the sandbox rail, and on `POST /api/reconcile`; `/api/provenance` serves the latest result, and Command shows it as `Transfers at the bank without a certificate`. The holder's own lookup (`reconcile_intent`) follows the same rule, so an intent is never released while its certificate could still move money. Each journal names its rail and is settled only on that rail. A transfer the bank lists later under a released certificate, for an intent that has paid again since, is reported as `paid_twice` (kept in the store, named in the view and in Command), never folded silently into the counts. The reconciler holds the desk lock only between bank calls: it reads the journals, asks the bank with the lock released, then re-reads each journal under the lock before it seals anything, so the desk keeps answering during a slow bank; one round runs at a time, and `POST /api/reconcile` answers `409 reconcile busy` while one is in flight. A bank answer that is not a list of transfers counts as `bank: unavailable`; a stored journal or receipt that does not parse is named in `unreadable` and the rest of the round runs; any other failure of a round is logged by its type and kept as the latest view (`reconcile: failed` with its time), so Command never shows an old check as current. Remaining seams: the store itself is trusted. Seals detect an edit inside the sealed range, and an entry past the last seal, but not a consistent truncation (entries, seals and records removed together) or a restored older copy of `state.db`; catching those needs the latest seal and its sealed count anchored outside the store. Restoring an older copy also un-spends certificates, consents, intents and idempotency keys, so a paid intent could pay again under a new certificate; the reconciler would only show that afterwards, as an unbacked transfer since genesis. The fences (`used`) and the other records are not signed. A confirmed payment whose proof receipt could not be built counts as unbacked, because only receipts feed the comparison. Registry load recomputes one root per seal, so start-up time grows with the square of the entry count. Revocation indices still wrap at 1024 (revoking index i also revokes a later certificate with the same index); reconciliation starts at genesis, so transfers made from the account before the registry existed are not counted; Command's metric reflects the last check and shows its time, so a transfer made after it is counted at the next one; seals are signed only by the desk's own key.
- Bank lines are read, not pushed: the console polls Increase's List Events every 5 s (no webhook, so no public URL is needed), so a bank line appears up to 5 s after the bank lists the event. The cursor and the ids already shown are committed before a line is published, so a crash between the two loses that page's lines (with the rest of the in-memory feed) rather than repeating them.
- Public anchor (gate/anchor_public.py): what is stamped is the desk-bound anchor digest, never the bare root, because a leaf depends only on its entry and two desks with equal entries share a root. The digests go to four public aggregators nonce-blinded, and headers come from Blockstream's Esplora, trusted only for availability; the proof and the header's work are checked offline. A pending proof proves nothing yet. The explorer verifies only sha256, append and prepend operations, all current calendars emit; the desk refuses to record a confirmation with any other. The work floor is target 2^180 (difficulty about 1.76e13); the browser checks the header's own work and merkle root, not that the block is in Bitcoin's main chain, which a reader checks by the block hash at any block explorer. Only a desk with a state directory stamps, and only when started with `--public-anchor`, since stamping calls third parties; rounds run on a background thread every 600 s and on `POST /api/anchor`, never on the decision path; `POST /api/anchor` answers `409 anchor busy` while any round runs, the background one included. A round a third party kept from completing is logged at warning with its reason (`anchor round incomplete (<reason>)`), one that raised by its type only (`anchor round failed (<type>)`), and either is retried. A calendar answer whose merge the explorer could not read (another operation, a repeated operation, nesting past 255 operations, a proof over 32768 bytes) counts as no answer and is never stored. A desk that wrote a false entry before stamping is not caught; rewriting the log after the stamp is.
- Console (swarm/console.py, console/): attacks started from the console are deterministic templates and are labeled `TEMPLATE`; the replay template pays the legitimate 200.00 once per click before replaying its certificate. Console state is in memory and line numbers restart with each process, so clients restart from zero when the stream announces a new epoch. The journal tail publishes only hook records under the `hook` source; anything else in the journal, including a console line claiming another source, is skipped. Replay mode (`?replay=<name>`) plays a recorded stream and says `REPLAY` for as long as it is active.
- Attack panel routes (swarm/server.py, swarm/live_attack.py): `GET /api/attack` lists the pinned templates and whether the live attacker is available; `POST /api/attack/model {"kind"}` asks the open-weights attacker (`swarm/live_attack.py`) for a plan, one request at a time, and publishes a line only when the reply yields a plan that the gate then decides. The live attacker exists only with `--live-attacker`; templates never call a model. The kill-cam is built in the browser from the forensic block of the line, so it adds no route.
- Nimbus deploy (swarm/nimbus.py): steps are pinned and labelled `SCENARIO`; prod-eu is simulated and verifies the release certificate offline. The Nimbus policy names the current migration, so a superseded one matches no rule. The release intent carries no money because deploy rules never read it. A live Muse Code deploy is governed by the hook's cmd atoms, which see only the first binary of each shell segment.
- Holder approval panel (console/src/approval/): the hash it shows is the consent hash (sha256 of the seven signed consent fields), not the action hash; the canonical action and its hash exist only at confirm and appear in the forensic drawer. Device state (`GET /api/device`) is pairing only, not liveness: the desk cannot tell whether the paired device is watching. Local expiry is shown on the console's clock and enforced only by the desk and the gate.
- Voice confirmation (swarm/voice.py, swarm/server.py, webapp/app.js): the transcript is a displayed confirmation, never compared with the consent fields and never an authority; push-to-talk mode (`PUSH_TO_TALK`) returns no speaker attribution. The clip leaves the device for the desk and Meta and is not stored. Voice spend is limited to the paired device: `POST /api/voice` transcribes only a clip whose `mandate/voice/v1` signature (quote id and sha256 of the received body) verifies against a paired holder key, checked before any model call, one call at a time (a second upload is refused before its body is read), each signed clip once per pending quote, never for a quote past its deadline, and only on a desk started with `--voice`; `GET /api/device` reports that flag so the holder page offers the microphone only when it is on. The holder page also sends `frame-ancestors 'none'`. That signature authenticates the uploading device, not the speaker, and is never a consent.
- Holder ids and device fingerprints appear only on the operator's terminal; the console, Command and receipts carry counts.
- Spawn binding assumes children are created only through subagent_spawn: SubagentStart carries no parent id, so the next UUID child claims the single pending spawn.
- Command reads the console's retained window (newest 2000 lines) and the registry and policies of this process; it keeps no all-time totals, the served policies are this process's desk, payments and Nimbus policies (Muse Code hook policies live in the hook process; their lines name the policy id only), and the framework mapping lists the gap of every provision it cites.
